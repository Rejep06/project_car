# Комиссия, непрочитанные сообщения и исправление выводов

Обновление от 11 октября 2026 года.

## 1. Комиссия вывода — 10%

Для новых заявок комиссия рассчитывается от суммы, которую получит пользователь.
Она добавляется сверху к списанию с внутреннего баланса.

| Получателю, USDT | Комиссия 10%, USDT | Всего с баланса, USDT |
| --- | --- | --- |
| 20 | 2 | 22 |
| 50 | 5 | 55 |
| 100 | 10 | 110 |
| 200 | 20 | 220 |

В `backend/.env` используется настройка:

```env
WITHDRAWAL_FEE_PERCENT=10
```

Если строки нет, значение по умолчанию тоже 10. Старую строку
`WITHDRAWAL_FEE=2.000000` удалите: фиксированная комиссия больше не используется.
В публичном API `/api/v1/system/config` поле `withdrawal_fee_percent` заменило
`withdrawal_fee`, поэтому backend и оба frontend нужно обновить вместе.

Расчёт на сервере и в интерфейсе выполняется целыми числами. Результат округляется
до 0.000001 USDT; половина минимальной единицы округляется вверх. Например,
10% от 20.000005 USDT = 2.000001 USDT после округления.

Ранее созданные заявки сохраняют записанную комиссию. Устанавливать новую комиссию
в старой заявке можно через редактор, описанный ниже. При отметке отправки поле
фактической комиссии сразу заполнено комиссией выбранной заявки.

## 2. Подсветка и счётчики непрочитанного

В личном кабинете пункты «Уведомления» и «Поддержка» выделяются цветом, а справа
показывается число непрочитанных. В админке такое же поведение у «Поддержки».
Считаются отдельные входящие сообщения. Для количества больше 99 показывается
`99+`; точное число остаётся в подписи для средств доступности.

Счётчики обновляются каждые 30 секунд, при возвращении во вкладку, переходе между
разделами и сразу после успешного прочтения. На кнопке мобильного меню появляется
точка, когда есть новые сообщения. В списке обращений выделяется конкретное
обращение и показывается его счётчик.

Ответ поддержки отмечается прочитанным, когда появляется в области просмотра
открытой переписки в видимой вкладке. Сообщения, которые ещё не видны, сохраняют
свой счётчик. В браузере без IntersectionObserver прочитанными становятся
загруженные входящие сообщения открытой видимой переписки. Исходящие сообщения
не увеличивают собственный счётчик. У администраторов общий признак прочтения
сообщений клиентов.

Для системного уведомления используются «Отметить прочитанным», «Открыть» или
«Прочитать все». Состояние прочтения хранится в базе и сохраняется после выхода.

Миграция `0007_support_message_reads` добавляет `read_at` сообщениям поддержки.
История, которая уже находилась в базе до обновления, принимается за прочитанную:
определить задним числом, что пользователь действительно видел, прежняя версия
приложения не позволяет. Счётчики начинают учитывать новые сообщения после
обновления. Тексты обращений и вложения сохраняются.

## 3. Как изменить вывод другого пользователя

1. Войдите в административную панель.
2. Откройте «Выводы». Список идёт от новых заявок к старым.
3. Найдите нужный email и откройте заявку. Проверьте ID, адрес и статус.
4. Нажмите «Изменить сумму и комиссию».
5. Введите новую сумму получателю и новую комиссию в USDT.
6. При необходимости нажмите «Рассчитать 10% от новой суммы».
7. Укажите причину изменения и проверьте таблицу «Сейчас / После изменения»
   и сумму возврата или дополнительного списания.
8. Нажмите «Сохранить изменения».

Например, старый вывод: получателю 100, комиссия 2, всего 102 USDT. Если изменить
комиссию на 10 USDT, итог станет 110 USDT, а дополнительно будет удержано или
списано 8 USDT. Если изменить получателю на 80 и комиссию на 8, итог станет
88 USDT, а пользователю вернутся 14 USDT.

| Статус заявки | Что делает исправление |
| --- | --- |
| Ожидает проверки / подтверждена / отправлена | Пересчитывает удержанную сумму и доступный баланс на разницу |
| Завершена | Пересчитывает доступный баланс относительно прежнего фактического списания; резервы других заявок сохраняются |
| Отменена / отклонена | Редактирование сумм недоступно, поскольку деньги по заявке уже возвращены |

Для уже отправленного вывода это исправление внутреннего учёта: сумма реального
блокчейн-перевода по TxID от него не меняется. Сверяйте запись с фактической выплатой.

При недостатке доступного баланса увеличение суммы отклоняется. Заявка, баланс
и аудит сохраняются одной транзакцией. Старые операции остаются в истории;
исправление создаёт отдельную операцию корректировки и запись `withdrawal_amounts_updated`
в разделе «Аудит», с прежними и новыми значениями и причиной.

Повторное нажатие после сетевой ошибки не списывает деньги второй раз. Если
другой администратор успел изменить заявку, редактор попросит обновить страницу.

## 4. Обновление работающего сервера

Команды выполняются из корня проекта — папки с `docker-compose.yml`.
Используйте те же параметры `docker compose -f ...`, если ваш сервер запускается
с дополнительным compose-файлом.

### Сохранить данные и загрузить код

Перед обновлением сохраните копию текущего кода и настроек. Пример резервной
копии базы из работающего контейнера:

```bash
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB"' > automotive_before_update_2026-10-11.sql
```

Перенесите обновлённые исходники из архива в проект. Сохраните действующие
корневой `.env`, `backend/.env`, настройки серверного compose и файлы загрузок.
Добавьте `WITHDRAWAL_FEE_PERCENT=10` в `backend/.env`.

### Собрать, применить миграцию и запустить

Сначала соберите образы, пока прежняя версия продолжает работать:

```bash
docker compose build api deposit-worker reward-worker email-worker customer-frontend admin-frontend
```

После успешной сборки остановите приложения на время изменения схемы:

```bash
docker compose stop customer-frontend admin-frontend api deposit-worker reward-worker email-worker
docker compose up -d db
docker compose run --rm api alembic upgrade head
docker compose run --rm api alembic current
```

Ожидаемая миграция — `0007_support_message_reads (head)`. Если миграция завершилась
ошибкой, сначала исправьте её причину; новую версию frontend ещё не запускайте.
После успешной миграции:

```bash
docker compose up -d api deposit-worker reward-worker email-worker customer-frontend admin-frontend
docker compose ps
docker compose logs api --tail=50
```

Для этого обновления удалять volumes или создавать новую базу не требуется.
После запуска обновите страницу браузера, чтобы загрузились новые скрипты.

### Проверка после установки

- В форме вывода для 100 USDT отображаются комиссия 10 USDT и итог 110 USDT.
- Новый ответ администратора даёт пользователю подсветку «Поддержки» и счётчик.
- После просмотра ответа счётчик уменьшается; новые системные уведомления
  аналогично выделяют «Уведомления».
- В админке карточка действующего или завершённого вывода содержит кнопку
  «Изменить сумму и комиссию».

## 5. API для интеграций

Исправление вывода доступно только администратору:

```http
PATCH /api/v1/admin/withdrawals/{withdrawal_id}/amounts
Authorization: Bearer <access_token>
Idempotency-Key: <уникальный ключ операции>
Content-Type: application/json
```

```json
{
  "amount": "100.000000",
  "fee": "10.000000",
  "comment": "Исправление комиссии по обращению клиента",
  "expected_updated_at": "<updated_at из последнего GET заявки>"
}
```

При повторе того же запроса после сбоя связи используйте тот же ключ и тело.
Для нового исправления получите свежую заявку и новый ключ.

Непрочитанные сообщения поддержки:

| Метод | Endpoint | Данные |
| --- | --- | --- |
| GET | `/api/v1/support/unread-count` | `{ "unread_count": 3 }` |
| POST | `/api/v1/support/tickets/{ticket_id}/read` | Тело `{ "message_ids": ["UUID"] }`, ответ с общим `unread_count` |
| GET | `/api/v1/admin/support/unread-count` | Общий счётчик входящих сообщений клиентов |
| POST | `/api/v1/admin/support/tickets/{ticket_id}/read` | Прочтение перечисленных входящих сообщений |

Запрос прочтения принимает до 1000 ID. Новое сообщение, пришедшее после загрузки
переписки, не теряет отметку непрочитанного, поскольку его ID отсутствует в запросе.
Полная схема находится в `BACKEND_OPENAPI.json`, перечень маршрутов — в
`BACKEND_API_MAP.md`.

## 6. Результаты проверки

- Backend: полный набор из 107 тестов прошёл на изолированной SQLite-базе.
- Личный кабинет: 36 тестов прошли.
- Административная панель: 29 тестов прошли.
- Обе production-сборки, TypeScript и ESLint прошли.
- Миграции применены с нуля до `0007_support_message_reads`; `alembic check` не
  выявил расхождений модели и базы. Отдельно проверены backfill старых сообщений,
  новые сообщения с NULL и downgrade новой миграции. PostgreSQL SQL новой
  миграции проверен через offline-генерацию.
- Проверены округление комиссии, доступный/заблокированный баланс, отмена и
  завершение вывода, корректировка уже завершённого вывода, повтор запроса,
  недостаток средств, доступ администратора, аудит, устаревшая форма и ответ
  предыдущей страницы после перехода к другой заявке.

Прогоны не использовали рабочую базу или реальные платежи. Интеграционные
backend-тесты выполнены на SQLite; конкурентный прогон на живом PostgreSQL
и отправка реальных блокчейн-транзакций в эту проверку не входили.
Визуальный прогон Chromium в этой среде не выполнен: браузер завершался
при запуске. Проверки frontend-компонентов выполнены через Vitest/jsdom.

Для повторения стандартных тестов после установки зависимостей:

```bash
cd backend
python -m pytest
cd ../customer-frontend
npm ci
npm run build
npm test
npm run lint
cd ../admin-frontend
npm ci
npm run build
npm test
npm run lint
```

Для проверок также актуализированы устаревшие тестовые данные регистрации,
пополнений и прежнего Binance HTTP-клиента. Приложение по-прежнему использует
активную конфигурацию Infura/Ethereum. Зависимость SQLAlchemy объявлена с
расширением `[asyncio]`, которое устанавливает необходимый `greenlet`.
