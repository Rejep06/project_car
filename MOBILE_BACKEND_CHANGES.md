# Минимальные изменения backend для Automotive Mobile

Изменения сохраняют существующие маршруты, тела запросов и ответы сайта/админки. Новые пользователи, балансы, подписки или отдельная база для телефона не создаются.

## Что изменено

1. `POST /api/v1/wallet/deposits` принимает необязательный `Idempotency-Key`. Ключ и отпечаток нормализованного запроса сохраняются в заявке атомарно с резервированием суммы. Повтор возвращает ту же заявку и точную сумму; другое тело или пользователь получают 409. В PostgreSQL запросы одного пользователя сериализуются существующей блокировкой строки кошелька; уникальность ключа дополнительно обеспечена БД.
2. `POST /api/v1/wallet/withdrawals` принимает необязательный `Idempotency-Key`. Ключ связан с неизменным журналом первой блокировки денег; дополнительная схема вывода не нужна. Повтор не удерживает деньги снова, восстанавливает актуальную запись после закрытия дня подачи и после административной корректировки/отклонения. Сравниваются исходная сумма и адрес.
3. Покупка билетов уже имела обязательный ключ, но повторы проверялись после закрытия продаж/лимитов и не проверяли изменённое количество. Исправлено: committed replay восстанавливается до проверки доступности новой покупки; изменённая лотерея/количество/пользователь отвергаются.
4. Покупка программы уже имела обязательный ключ. Восстановление committed replay теперь также возможно после заморозки аккаунта; новые покупки замороженного пользователя запрещены.
5. `/api/v1/system/config` дополнен `financial_request_idempotency_supported: true`. Мобильное приложение проверяет этот признак перед пополнением и выводом, чтобы старый сервер не проигнорировал защитный заголовок.
6. Добавлены сценарии реального ASGI API в `backend/tests/test_mobile_idempotency.py`.

JWT уже возвращал обе пары токенов в JSON. `/auth/refresh` и `/auth/logout` уже принимали `{refresh_token}`; изменения авторизации для native не потребовались. Веб-клиент, сайт и административная панель не изменялись.

## Миграция

Добавлена `0008_mobile_deposit_idempotency`, следующая за `0007_support_message_reads`. Она добавляет только две nullable-колонки `request_idempotency_key`, `request_fingerprint` и уникальность ключа в `deposit_invoices`. Существующие заявки не переписываются. Старые выводы, суммы и комиссии не изменяются.

Перед запуском мобильного приложения обновить код API и применить миграцию к **существующей** базе. Сначала сделать штатную резервную копию вашей рабочей БД.

Для установки Python без Docker:

```bash
cd backend
python -m pip install -r requirements.txt
python -m alembic upgrade head
```

Затем перезапустить API штатным способом вашего сервера. Для корневого Docker Compose проекта:

```bash
docker compose build api
docker compose run --rm api python -m alembic upgrade head
docker compose up -d api
```

Проверить `GET https://<ваш-api>/api/v1/system/config`: признак должен быть `true`. Для старого сайта ключи новых wallet POST остаются необязательными; мобильный клиент передаёт их всегда. Сайт и приложение видят одну и ту же историю.

## Комиссии, статусы и безопасность

Комиссия уже была реализована как серверный процент: `WITHDRAWAL_FEE_PERCENT=10` по умолчанию, целочисленное half-up округление до `0.000001 USDT`. `amount` — получателю, `fee` — сверху, `held_total` — первоначальное удержание, `final_total` — текущая сумма плюс текущая комиссия. Проверка доступного баланса, дня недели и минимума остаётся серверной. Администратор может изменить прошлые данные согласно существующей бизнес-логике; мобильный пользователь получает только чтение собственной истории и существующую отмену pending-заявки.

Права на административные маршруты и вложения поддержки сохраняются. Ключи идемпотентности не дают права просмотреть чужую заявку. В production по-прежнему требуется HTTPS и работа существующих deposit/reward/email workers. HTTP разрешён в приложении только для локальной разработки.

## Push: что потребуется на сервере

В текущем проекте нет серверной инфраструктуры push. В готовом клиенте работают существующие REST-уведомления, счётчики и обновление чата при открытом приложении. Push при закрытом приложении не заявляется реализованным.

Для будущего push дополнения понадобится:

- Защищённая регистрация/удаление device token текущего пользователя, платформа и идентификатор установки; хранение токенов только в серверной БД.
- Очередь доставки после создания уведомления/ответа поддержки, обработка недействительных токенов и повторов.
- Выбор Expo Push или прямого APNs/FCM, серверные credentials, consent пользователя и Expo development/production builds.
- Безопасная payload с ID записи и маршрутом; тексты финансовых/личных данных не включать по умолчанию. После открытия приложение получает действительную запись из REST API.

Такие маршруты не придуманы и не вызываются мобильным клиентом в этой версии. Для push нужен отдельный серверный релиз с настроенными credentials.

## Проверки и границы проверки

Сценарии выполняются в изолированной SQLite БД через настоящее FastAPI ASGI приложение. Регистрация/подтверждение/вход, refresh, восстановление, права, начисления, пополнения, выводы, поддержку, вложения, уведомления, лотереи и защиту повторов проверяют backend tests. Точные команды/результат итогового запуска указаны в `automotive_mobile/docs/TESTING.md`.

Не выполнялись реальные blockchain переводы, production списания, отправка SMTP, APNs/FCM или финансовые операции на живом сервере. Тесты провайдеров используют изолированные адаптеры и данные, а не рабочие реквизиты. Конкурентные блокировки PostgreSQL на production и миграция рабочей базы не выполнялись; миграционный smoke запуск проверяется на отдельной SQLite БД.
